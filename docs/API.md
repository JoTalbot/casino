# API игрового сервера (RGS)

**Версия:** 1 · **Дата:** 2026-08-17 · **Агент:** claude-2026-08-17-B · **Задача:** T-013
**Машиночитаемая спецификация:** [`api/openapi.yaml`](../api/openapi.yaml)
**Схема БД:** [`docs/DB-SCHEMA.md`](DB-SCHEMA.md) · **RNG:** `src/engine/rng.ts`

---

## 1. Главный принцип

> **Клиент ничего не решает. Клиент показывает то, что сказал сервер.**

Клиент не считает выигрыш, не выбирает символы, не знает лент, не генерирует
случайность. Он отправляет «крутить» и получает готовый результат, который
рисует с анимацией. Любая попытка перенести хоть часть логики на клиент делает
игру невозможной для сертификации и тривиально ломаемой (`research/01`, ADR-002).

Практическое следствие: если библиотека рендера умеет сама выбирать символы по
весам — эту возможность отключаем и подаём готовую сетку (см. `research/06` §2
про `pixi-reels`).

## 2. Транспорт и общие соглашения

| Параметр | Значение |
|---|---|
| Протокол | HTTPS, REST + JSON |
| База | `/api/v1` |
| Кодировка | UTF-8 |
| Время | ISO 8601 в UTC, суффикс `Z` |
| Именование полей | `camelCase` |
| Аутентификация | `Authorization: Bearer <JWT>` |
| Идемпотентность | заголовок `Idempotency-Key` на всех мутирующих запросах |

**WebSocket не нужен.** Слот — это классический запрос-ответ: игрок нажал,
сервер ответил. WebSocket обязателен для crash/live-игр, где состояние меняется
без действий игрока. Добавить его позже можно, не ломая REST (`research/01`).

### Денежные величины

Все суммы — **целые числа в минимальных единицах** валюты, поле `exponent`
приходит вместе с балансом. Для фишек `CHIP` exponent = 0.

```json
{ "currency": "CHIP", "exponent": 0, "balance": 12500 }
```

Ни одного дробного числа в денежных полях. Клиент форматирует сам.

### Формат ошибки

Единый для всех эндпоинтов:

```json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "Недостаточно фишек на балансе",
    "details": { "required": 200, "available": 150 }
  }
}
```

| Код | HTTP | Когда |
|---|---|---|
| `UNAUTHENTICATED` | 401 | нет или истёк токен |
| `FORBIDDEN` | 403 | действие запрещено (самоисключение, блокировка) |
| `NOT_FOUND` | 404 | раунд/игра/пара сидов не найдены |
| `VALIDATION_FAILED` | 400 | некорректные параметры |
| `INSUFFICIENT_FUNDS` | 409 | не хватает баланса |
| `LIMIT_EXCEEDED` | 409 | превышен лимит ответственной игры |
| `ROUND_IN_PROGRESS` | 409 | предыдущий раунд не завершён |
| `IDEMPOTENCY_CONFLICT` | 409 | тот же ключ с другими параметрами |
| `GAME_DISABLED` | 409 | игра выключена |
| `RATE_LIMITED` | 429 | слишком часто |
| `INTERNAL` | 500 | всё остальное |

### Идемпотентность

Обязательна для `POST /rounds` (спин). Клиент генерирует UUID и **при ретрае
шлёт тот же самый**. Сервер:

1. ключ не встречался → выполняет и запоминает результат;
2. ключ встречался, параметры те же → возвращает **сохранённый ответ**,
   ставку повторно не списывает;
3. ключ встречался, параметры другие → `409 IDEMPOTENCY_CONFLICT`.

Это тот самый `PLACE / SETTLE / ROLLBACK` с гарантией идемпотентности из
`nekzabirov/IGaming-Game-Engine` (`research/06` §1.2). Без него порванная сеть
превращается в двойное списание.

### Ограничение частоты

`POST /rounds` — не чаще 10 запросов в секунду на игрока (реальный слот —
примерно один спин в 2–3 секунды; 10/с покрывает автоспин и турбо с запасом).
Ответ 429 содержит `Retry-After`.

## 3. Эндпоинты

### 3.1 Каталог игр

```
GET /api/v1/games
```

```json
{
  "games": [
    {
      "code": "crown-of-fortune",
      "title": "Crown of Fortune",
      "reels": 5, "rows": 3, "lines": 20,
      "enabled": true,
      "thumbnailUrl": "/assets/crown-of-fortune/thumb.webp"

```

```
GET /api/v1/games/{gameCode}
```

заявленный RTP, индекс волатильности и `configHash`.

  "version": "1.0.0",

    "K":       { "3": 20,  "4": 70,  "5": 225  },
    "Q":       { "3": 15,  "4": 55,  "5": 175  },
    "J":       { "4": 40,  "5": 138 },
    "TEN":     { "4": 35,  "5": 113 }

  "scatterPays": { "3": 2, "4": 10, "5": 50 },
  "freeSpins": {
    "trigger": 3,
    "award": { "3": 10, "4": 15, "5": 25 },

юрисдикций.

### 3.2 Provably fair: пара сидов

```
GET /api/v1/seeds/current
```

```json
{
  "seedPairId": "018f...",
  "serverSeedHash": "9c1185a5c5e9fc54612808977ee8f548b2258d31",
  "clientSeed": "my-lucky-seed",
  "nextNonce": 137,
  "createdAt": "2026-08-17T10:00:00Z",
  "nextServerSeedHash": "a3f5..."
}
```

**`serverSeed` здесь не возвращается никогда.** Только его хэш — это и есть
коммитмент, сделанный до ставок.

`nextServerSeedHash` — хэш уже сгенерированной *следующей* пары. Приятная
деталь: игрок видит коммитмент будущей пары ещё до ротации, то есть сервер
не может подобрать «удобный» сид в момент ротации.

```
POST /api/v1/seeds/client
{ "clientSeed": "my-lucky-seed" }
```

Меняет клиентский сид. Ограничения (продублированы в БД и в `rng.ts`):
1–256 символов, **двоеточие запрещено**. Причина в §3.3 `docs/DB-SCHEMA.md`.

```
POST /api/v1/seeds/rotate
```

Ротация. Атомарно: текущая пара помечается `revealed`, создаётся новая.
Ответ содержит **раскрытый серверный сид старой пары** и коммитмент новой.

```json
{
  "revealed": {
    "seedPairId": "018f...",
    "serverSeed": "3a7bd3e2360a3d29eea436fcfb7e44c735d117c42d1c1835420b6b9942dd4f1b",
    "serverSeedHash": "9c1185a5...",
    "clientSeed": "my-lucky-seed",
    "noncesUsed": 137
  },
  "current": {
    "seedPairId": "018g...",
    "serverSeedHash": "a3f5...",
    "clientSeed": "my-lucky-seed",
    "nextNonce": 0
  }
}
```

С этого момента игрок может проверить **все 137 раундов** старой пары —
самостоятельно, без обращения к нам.

```
GET /api/v1/seeds/history?limit=50&cursor=...
```

Все прошлые пары с раскрытыми сидами. Не чистится никогда: без истории
provably fair — пустой лозунг (`research/06` §3).

### 3.3 Спин

```
POST /api/v1/rounds
Idempotency-Key: 7f3a9c21-...
{
  "gameCode": "crown-of-fortune",
  "betPerLine": 10,
  "lines": 20
}
```

Ответ `201`:

```json
{
  "roundId": "018f2c...",
  "gameCode": "crown-of-fortune",
  "configHash": "5f9b9c35...",
  "status": "settled",
  "bet": { "perLine": 10, "lines": 20, "total": 200 },
  "fairness": {
    "seedPairId": "018f...",
    "serverSeedHash": "9c1185a5...",
    "clientSeed": "my-lucky-seed",
    "nonce": 137,
    "drawCount": 5
  },
  "spins": [
    {
      "index": 0,
      "free": false,
      "reelStops": [12, 3, 30, 7, 21],
      "grid": [
        ["K","WILD","Q"],
        ["A","A","TEN"],
        ["A","J","SCATTER"],
        ["Q","K","A"],
        ["TEN","A","J"]
      ],
      "win": 500,
      "multiplier": 1,
      "scatterCount": 1,
      "triggeredFreeSpins": 0,
      "winDetails": [
        { "line": 4, "symbol": "A", "count": 3, "positions": [[0,1],[1,1],[2,1]], "pay": 250 },
        { "line": 9, "symbol": "A", "count": 3, "positions": [[0,1],[1,0],[2,0]], "pay": 250 }
      ]
    }
  ],
  "totalWin": 500,
  "balance": { "currency": "CHIP", "exponent": 0, "amount": 12800 },
  "settledAt": "2026-08-17T12:34:56Z"
}
```

Ключевые решения:

- **Один запрос = весь раунд.** Базовый спин и вся серия фриспинов возвращаются
  сразу, в массиве `spins`. Клиент проигрывает их анимацией последовательно.
  Так раунд атомарен и не может «зависнуть» посреди бонуса, если игрок закрыл
  вкладку. Соответствует модели раунда в БД и работе `RoundRandom`.
- **`grid` — матрица по барабанам**, `grid[reel][row]`. Порядок совпадает
  с `reelStops`.
- **`positions`** в `winDetails` — координаты `[reel, row]`, чтобы клиент
  подсветил выигрышную линию, не пересчитывая её.
- **`fairness` возвращается всегда**, прямо в ответе на спин. Игрок видит
  nonce и коммитмент сразу, а не идёт искать их в истории.
- `balance` — состояние **после** раунда, чтобы клиент не делал второй запрос.

Проверки перед списанием, по порядку:
статус игрока → самоисключение → лимиты (`LIMIT_EXCEEDED`) → нет открытого
раунда (`ROUND_IN_PROGRESS`) → игра включена → корректность ставки
(`betPerLine` из `betLevels`, `lines` в допустимом диапазоне) → достаточность
баланса. Всё в одной транзакции с расчётом.

### 3.4 История раундов

```
GET /api/v1/rounds?limit=50&cursor=...&gameCode=crown-of-fortune
```

Курсорная пагинация (не offset: на длинной истории offset деградирует и
«съезжает» при вставках). Курсор непрозрачный, кодирует `(started_at, id)`.

```json
{
  "rounds": [
    {
      "roundId": "018f2c...",
      "gameCode": "crown-of-fortune",
      "totalBet": 200,
      "totalWin": 500,
      "spinsCount": 1,
      "nonce": 137,
      "serverSeedHash": "9c1185a5...",
      "serverSeedRevealed": false,
      "startedAt": "2026-08-17T12:34:56Z"
    }
  ],
  "nextCursor": "eyJ0IjoiMjAyNi0wOC0xN1QxMjozNDo1NloiLCJpIjoiMDE4ZjJjIn0"
}
```

```
GET /api/v1/rounds/{roundId}
```

Полная карточка раунда — тот же объект, что вернул спин, плюс поле
`serverSeed`, **если** пара сидов уже раскрыта. Именно отсюда игрок берёт
данные для проверки.

### 3.5 Верификация

```
POST /api/v1/verify
{
  "serverSeed": "3a7bd3e2...",
  "clientSeed": "my-lucky-seed",
  "nonce": 137,
  "gameCode": "crown-of-fortune",
  "configHash": "5f9b9c35..."
}
```

```json
{
  "valid": true,
  "serverSeedHash": "9c1185a5...",
  "reelStops": [12, 3, 30, 7, 21],
  "grid": [["K","WILD","Q"], ...],
  "totalWin": 500,
  "drawCount": 5
}
```

Эндпоинт **не требует аутентификации** — проверить раунд должен уметь кто
угодно, включая журналиста и скептика с форума. Он ничего не читает из базы,
только пересчитывает по входным данным.

Важно: наличие серверного эндпоинта верификации **не заменяет** независимую
проверку. Поэтому в T-021 делается автономный HTML-файл, который игрок
скачивает и запускает у себя — там наш сервер не участвует вообще.

Формат совместим со сторонними верификаторами Stake-типа
(`research/06` §3), потому что сообщение HMAC у нас каноническое:
`HMAC_SHA256(serverSeed, "clientSeed:nonce:cursor")`.

### 3.6 Кошелёк

```
GET /api/v1/wallet
{ "currency": "CHIP", "exponent": 0, "balance": 12800 }

GET /api/v1/wallet/transactions?limit=50&cursor=...
```

На стадии 1 (соц-казино, ADR-004) пополнение — только через `grant`:
стартовый пакет при регистрации и ежедневный бонус. Эндпоинтов покупки
и вывода **нет намеренно**, и это принципиально: их отсутствие — то, что
отличает соц-казино от азартной игры юридически.

### 3.7 Ответственная игра

```
GET  /api/v1/limits
POST /api/v1/limits          { "kind": "loss_daily", "value": 5000 }
POST /api/v1/self-exclusion  { "durationDays": 30 }
```

Правило, зашитое и в API, и в БД: **ужесточение лимита действует немедленно,
ослабление — только после периода охлаждения** (`cooling_until`, 24 часа).
Попытка ослабить раньше — `403 FORBIDDEN` с датой, когда станет можно.
Самоисключение необратимо до истечения срока.

### 3.8 Сообщество: турниры, рефералы, ачивки, чат, push

Добавлено в T-055…T-079, задокументировано в T-181. Все ответы — JSON,
денежные величины — целые CHIP.

| Метод | Путь | Авторизация | Назначение |
|---|---|---|---|
| GET | `/api/v1/tournaments` | нет | список турниров |
| GET | `/api/v1/tournaments/:code/leaderboard?limit=` | нет | таблица турнира, `404` если код неизвестен |
| GET | `/api/v1/leaderboard?by=win\|bet&period=day\|week\|all` | нет | общий топ |
| POST | `/api/v1/referrals` | JWT | привязка реферала |
| GET | `/api/v1/referrals` | JWT | кого пригласил + свой код |
| GET | `/api/v1/referrals/progress` | JWT | прогресс до ачивки «Мастер рефералов» |
| GET | `/api/v1/referrals/leaderboard?limit=` | нет | топ пригласивших |
| GET | `/api/v1/achievements` | JWT | все ачивки со статусом |
| GET | `/api/v1/chat?limit=` | нет | последние сообщения (по возрастанию времени) |
| POST | `/api/v1/chat` | JWT | отправить сообщение |
| POST | `/api/v1/push/subscribe` | JWT | подписка на web-push |
| DELETE | `/api/v1/push/subscribe` | JWT | отписка по `endpoint` |
| GET | `/api/v1/push/subscriptions` | JWT | активные подписки игрока |

**POST `/api/v1/referrals`** принимает либо `{"referralCode": "<id пригласившего>"}`
(текущий игрок — приглашённый), либо `{"refereeId": "<id новичка>"}`
(текущий игрок — пригласивший). Бонус: 5000 CHIP пригласившему, 1000 CHIP
приглашённому, обе проводки в одной транзакции с идемпотентными ключами
вида `referral:<referrer>:<referee>:<wallet-owner>`.

Правила защиты от накрутки (T-180):

| Код ошибки | HTTP | Когда |
|---|---|---|
| `SELF_REFERRAL` | 400 | игрок указал сам себя |
| `REFERRER_NOT_FOUND` | 404 | пригласивший не найден |
| `REFEREE_NOT_FOUND` | 404 | приглашённый не найден |
| `REFEREE_NOT_NEW` | 409 | у приглашённого уже есть сыгранные раунды |
| `ALREADY_REFERRED` | 409 | приглашённый уже привязан к другому игроку |

**POST `/api/v1/chat`**: сообщение обрезается по краям, длина 1…500 символов
после обрезки, стоп-слова отклоняются с `VALIDATION_FAILED`. Лимит —
5 сообщений в минуту на игрока, при превышении `429` и заголовок `Retry-After`.

**Push**: подписки хранятся в таблице `push_subscriptions` и переживают
рестарт API (T-178). Ключ уникальности — `endpoint`; повторная подписка
обновляет ключи, а не создаёт дубликат. Отправка уведомлений — заглушка
до появления VAPID-ключей в окружении деплоя.

Все соц-маршруты отвечают `503 DATABASE_UNAVAILABLE`, если API поднят
без PostgreSQL.

## 4. Последовательность обычного спина

```
Клиент                          Сервер                           БД
  │                               │                               │
  │ POST /rounds                  │                               │
  │ Idempotency-Key: 7f3a...      │                               │
  ├──────────────────────────────►│                               │
  │                               │ BEGIN                         │
  │                               ├──────────────────────────────►│
  │                               │ проверки: статус, лимиты,     │
  │                               │ открытый раунд, баланс        │
  │                               │                               │
  │                               │ SELECT ... FOR UPDATE         │
  │                               │   seed_pairs WHERE active     │
  │                               │ nonce := next_nonce++         │
  │                               │                               │
  │                               │ RoundRandom(serverSeed,       │
  │                               │   clientSeed, nonce)          │
  │                               │   → reelStops → grid → win    │
  │                               │                               │
  │                               │ INSERT rounds, spins          │
  │                               │ INSERT ledger 'bet'  (-200)   │
  │                               │ INSERT ledger 'win'  (+500)   │
  │                               │   триггер сверяет баланс      │
  │                               │ INSERT audit_log              │
  │                               │ COMMIT                        │
  │                               ├──────────────────────────────►│
  │ 201 + результат + баланс      │                               │
  │◄──────────────────────────────┤                               │
  │ анимация барабанов            │                               │
```

Вся денежная часть — **одна транзакция**. Либо раунд записан, деньги списаны
и выигрыш начислен, либо не произошло ничего. Промежуточных состояний нет.

`SELECT ... FOR UPDATE` на паре сидов сериализует спины одного игрока и
гарантирует уникальность nonce даже при параллельных запросах из двух вкладок.

## 5. Что сознательно НЕ делаем

| Решение | Почему |
|---|---|
| Клиент не присылает `nonce` | иначе игрок сможет переиграть удачный раунд |
| Клиент не присылает результат или сетку | это и есть главная дыра всех «казино-скриптов» |
| Нет эндпоинта «отменить спин» | результат окончателен; откат только серверный `ROLLBACK` при сбое |
| Нет WebSocket | слоту не нужен; добавится с live/crash-играми |
| Нет GraphQL | лишний слой, у REST здесь всего дюжина эндпоинтов |
| Нет покупки фишек | стадия 1 — соц-казино (ADR-004) |

## 6. Открытые вопросы к реализации

1. **Стек сервера** — T-010 (ADR не принят). Схема API от него не зависит.
2. **Автоспин** — сейчас это N обычных запросов от клиента. Пакетный эндпоинт
   `POST /rounds/batch` соблазнителен по трафику, но ломает лимиты
   ответственной игры и reality check. Решение: **не делать**, пока нет
   доказанной проблемы производительности.
3. **Демо-режим без регистрации** — вероятно нужен, но требует отдельного
   решения по кошельку (гостевой игрок с временным балансом). Отдельная задача.
