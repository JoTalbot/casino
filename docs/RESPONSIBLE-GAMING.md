# Ответственная игра

Модуль ограничений: лимиты, самоисключение, напоминание о времени в игре.
Реализация — `src/engine/responsible.ts` (чистая логика, 41 тест),
хранение — `db/schema.sql` (`player_limits`, `self_exclusions`, `sessions`),
транспорт — `docs/API.md` §3.7.

Документ описывает, **что** модуль гарантирует и **почему** правила
именно такие. Задача T-015.

---

## 1. Зачем это в проекте на виртуальных фишках

По ADR-004 стадия 1 — социальное казино: реальных денег нет, вывод
невозможен. Формально требования регуляторов к ответственной игре на
такой продукт не распространяются. Модуль всё равно сделан на первой
стадии, по трём причинам.

**Механика зависимости не зависит от валюты.** Петля «ставка — почти
выигрыш — следующая ставка» работает одинаково на фишках и на деньгах.
Соц-казино критикуют именно за это: игрок тренирует привычку в среде
без финансового тормоза, а потом переносит её туда, где тормоз нужен.

**Правила магазинов приложений это требуют.** Политики Apple и Google
для категории casino-style games включают ограничения по возрасту и
раскрытие того, что игра не даёт реальных выигрышей. Модуль лимитов —
часть той же группы требований (детали в T-016).

**Дорисовать это потом дороже, чем заложить сразу.** Лимит проверяется
до списания ставки, то есть внутри транзакции раунда. Встроить такую
проверку в существующий поток спинов означает переписать поток спинов.

## 2. Что модуль гарантирует

| Гарантия | Как обеспечена | Тест |
| :--- | :--- | :--- |
| Лимит нельзя превысить ни при каком исходе раунда | Проверка по худшему случаю до списания | «ставка, способная пробить лимит, не принимается» |
| Ужесточение действует немедленно | `applyLimitChange` → `effectiveFrom = now` | «снижение лимита действует немедленно» |
| Ослабление — только через 24 часа | Новая запись с `effectiveFrom` в будущем | «повышение лимита откладывается» |
| Таймер охлаждения нельзя сбросить повторным запросом | Отсчёт от `coolingUntil` действующего лимита | «повторный запрос не сбрасывает таймер» |
| Самоисключение нельзя сократить или снять | `applySelfExclusion` разрешает только удлинение | «нельзя сократить срок повторным запросом» |
| Крупный выигрыш не обнуляет лимит потерь | `lossToday` не уходит ниже нуля | «крупный выигрыш не уводит проигрыш в минус» |

Последние две строки — про обходные пути, а не про основной сценарий.
Ошибки в таких модулях обычно не в том, что запрет не срабатывает, а
в том, что его можно обойти.

## 3. Виды лимитов

Совпадают с ENUM `limit_kind` в схеме БД.

| Вид | Единица | Что ограничивает |
| :--- | :--- | :--- |
| `loss_daily` | кредиты | чистый проигрыш за календарные сутки |
| `loss_weekly` | кредиты | чистый проигрыш за календарную неделю |
| `wager_daily` | кредиты | оборот ставок за сутки |
| `spins_daily` | раунды | число раундов за сутки |
| `session_minutes` | минуты | длительность одной сессии |

Окна **календарные**, в часовом поясе оператора, а не «последние
24 часа». Скользящее окно технически честнее, но игрок не может
предсказать, когда лимит освободится, — а непредсказуемое ограничение
провоцирует именно то поведение, ради предотвращения которого оно
введено.

### Проверка по худшему исходу

Денежные лимиты проверяются с учётом будущей ставки:

```
lossToday + totalBet > limit  →  отказ
```

Не «остановиться по факту превышения», а «не допустить превышения ни
при каком исходе». Игрок с лимитом 1000 и потерями 900 не сможет
поставить 200, хотя *мог бы* выиграть. Регулятор трактует лимит потерь
именно так: сквозного пробоя быть не должно.

Сквозной тест это фиксирует: игрок с лимитом 1000, проигрывающий по 200,
останавливается ровно на 1000 — после пяти раундов, а не после шести
с перебором до 1200.

## 4. Период охлаждения

24 часа (`COOLING_MS`).

Асимметрия здесь намеренная и заимствована из требований UKGC и MGA:
решение ограничить себя принимается в спокойном состоянии и должно
исполняться немедленно; решение снять ограничение чаще принимается
в состоянии, ради которого ограничение и ставилось.

Механика хранения: ослабление **не заменяет** текущий лимит, а
добавляется рядом записью с `effectiveFrom` в будущем. Всё время
охлаждения действует старый лимит. Это проверяется на живом сервере,
а не только в юнит-тестах:

```
POST /limits {"kind":"spins_daily","value":3}      → immediate: true
... 3 спина сыграно, 4-й: HTTP 409
POST /limits {"kind":"spins_daily","value":1000}   → immediate: false
                                                     pending до +24 ч
POST /rounds                                       → HTTP 409, лимит 3
```

Повторный запрос на ослабление не сдвигает срок: отсчёт привязан к
`coolingUntil` действующего лимита, иначе таймер можно было бы
перезапускать бесконечно и тем самым обнулять ожидание.

Равное значение считается ослаблением. Иначе повтором того же числа
можно было бы держать себя в состоянии «немедленных изменений».

## 5. Самоисключение

`POST /api/v1/self-exclusion { "durationDays": 30 }`, `null` — бессрочно.

Необратимо до истечения срока. Разрешено только удлинение:

- срочное → более долгое срочное: применяется;
- срочное → более короткое: игнорируется, срок прежний;
- срочное → бессрочное: применяется;
- бессрочное → любое срочное: игнорируется.

Проверяется первым, раньше всех лимитов: исключённый игрок получает
`403 SELF_EXCLUDED`, а не сообщение о лимите.

Досрочное снятие не предусмотрено **и в интерфейсе поддержки тоже**.
Возможность снять исключение через оператора обесценивает сам
инструмент: игрок в срыве обратится в поддержку.

## 6. Reality check

Напоминание о времени в игре. По умолчанию раз в 60 минут
(`REALITY_CHECK_MS`, настраивается через env).

Отдаётся **вместе с ответом на спин**, отдельного опроса нет:
эндпоинт, который клиент должен вызывать сам, — это эндпоинт, который
клиент может не вызывать.

Содержание: сколько игрок играет, сколько раундов сыграно, сколько
поставлено, каков чистый результат. Формулировки нейтральные, без
«почти повезло» и без предложения продолжить. Цель — вернуть чувство
времени и суммы.

```
Вы играете 90 минут. Сегодня: 300 спинов, поставлено 6000 кредитов,
проигрыш 1200 кредитов.
```

Русские числительные склоняются (`1 спин` / `3 спина` / `5 спинов`) —
на это есть отдельный тест, потому что «5 спин» в напоминании об
ответственной игре выглядит несерьёзно ровно там, где нужен обратный
эффект.

## 7. Числа, которые стоит показывать игроку

Из расчёта T-019 (`docs/PAR-SHEET.md` §9.4), ставка 1 кредит за раунд:

| Депозит | Проигрался полностью | Медиана раундов | Ушёл в плюсе |
| ---: | ---: | ---: | ---: |
| 50 | 64.9% | 294 | 26.3% |
| 100 | 53.8% | 892 | 29.2% |
| 250 | 27.0% | 2 000 | 31.0% |
| 500 | 22.0% | 5 000 | 23.9% |
| 1 000 | 9.5% | 10 000 | 16.4% |

Строки между собой не сравнимы: в каждой растёт и депозит, и лимит
раундов. Больший депозит снижает риск проиграть всё, но удлиняет игру,
а с числом раундов вероятность уйти в плюсе падает. Предел один: доля
сессий, законченных в плюсе, нигде не выше 31% и стремится к нулю
с ростом дистанции.

Отдельно полезно объяснять разброс: на 1 000 раундов честный RTP
лежит в диапазоне **74.6–125.5%** (§9.2). Это ответ на жалобу «игра
занижает выплаты» — и одновременно ответ на «я нашёл выигрышную
стратегию».

## 8. Что НЕ сделано на этой стадии

| Функция | Почему отложена |
| :--- | :--- |
| Лимиты депозита | депозитов нет (соц-казино, ADR-004) |
| Проверка возраста / KYC | требует юр. трека, T-016 |
| Обнаружение проблемного поведения | нужна аналитика поведения, стадия 3+ |
| Уведомление близких, blocking software | требует лицензированного оператора |
| Календарные окна счётчиков | нужен планировщик и таймзона оператора; сейчас счётчики живут в памяти процесса |

Последний пункт — единственный технический долг модуля: в учебном
сервере счётчики не сбрасываются по границе суток, потому что сервер
вообще не переживает перезапуск. В боевой реализации `lossToday`
считается запросом к `ledger_entries` за текущие сутки, а не
инкрементом в памяти.
