# AGENTS.md — Обязательные инструкции для всех ИИ-агентов

> **ЧИТАЙ ЭТОТ ФАЙЛ ПЕРВЫМ. ЦЕЛИКОМ. ДО ЛЮБОГО ДЕЙСТВИЯ.**
> Этот файл — единственный источник правды о процессе работы в репозитории.
> Он написан для агентов (Claude, GPT, Gemini, Grok, Qwen, Kimi, Cursor, Copilot и др.),
> которые работают **с разных машин, в разное время и параллельно**.

## 0. TL;DR — протокол за 60 секунд

```bash
# 1. Синхронизация
git pull --rebase origin main

# 2. Прочитать контекст (ОБЯЗАТЕЛЬНО)
cat AGENTS.md                      # этот файл
cat agents/STATE.md                # текущее состояние проекта
cat agents/HANDOFF.md              # что оставил прошлый агент
cat agents/TASKS.md                # очередь задач
tail -50 agents/JOURNAL.md         # последние записи журнала
ls agents/locks/                   # кто сейчас что занял

# 3. Взять задачу и поставить лок
#    (см. раздел 4 «Блокировки»)

# 4. Работать. Коммитить часто, атомарно.

# 5. Закрыть смену: обновить STATE.md, HANDOFF.md, TASKS.md, JOURNAL.md,
#    снять лок, запушить.
```

**Золотое правило:** если ты не обновил `agents/STATE.md` и `agents/JOURNAL.md` —
твоя работа считается не сделанной, потому что следующий агент о ней не узнает.

## 1. О проекте

**Репозиторий:** `JoTalbot/casino`
**Тема:** исследование и разработка собственной онлайн-платформы казино (фокус — слоты).
**Текущая стадия:** R&D / прототип (см. `agents/STATE.md` для актуального статуса).

**Что здесь есть:**

| Путь | Назначение |
|---|---|
| `AGENTS.md` | Этот файл. Протокол работы агентов. |
| `agents/STATE.md` | Живое состояние проекта. Обновляется каждую смену. |
| `agents/HANDOFF.md` | Передача смены: контекст, ловушки, next steps. |
| `agents/TASKS.md` | Бэклог и очередь задач с ID. |
| `agents/JOURNAL.md` | Append-only журнал всех смен. Никогда не редактируй прошлые записи. |
| `agents/DECISIONS.md` | ADR — архитектурные решения и почему они приняты. |
| `agents/GLOSSARY.md` | Термины отрасли (RTP, GGR, PAR, hit frequency, …). |
| `agents/locks/` | Файлы-блокировки для параллельной работы. |
| `research/` | Результаты глубокого исследования (рынок, право, техника, комьюнити). |
| `docs/` | Проектная документация (архитектура, математика, API). |
| `src/` | Код прототипа. |
| `scripts/` | Утилиты (симуляторы, проверки, хелперы). |

## 2. Правила Git — жёстко

### 2.1 Всегда pull перед началом
```bash
git pull --rebase origin main
```
Никогда не начинай работу на устаревшем дереве. Работают параллельные агенты.

### 2.2 Пуш сразу, часто, мелкими коммитами
Правило заказчика: **все правки пушить сразу на GitHub**.
Не копи изменения локально. Один логический шаг = один коммит = один push.

```bash
git add -A
git commit -m "docs(research): добавлен раздел по RTP-моделям"
git push origin main
```

### 2.3 Формат сообщений коммита (Conventional Commits)

```
<тип>(<область>): <краткое описание на русском>

[тело — опционально]

Agent: <твоё имя-агента>
Task: <ID задачи из TASKS.md>
```

Типы: `feat`, `fix`, `docs`, `research`, `refactor`, `test`, `chore`, `state`.
Области: `agents`, `research`, `docs`, `engine`, `math`, `api`, `ui`, `infra`.

Пример:
```
feat(engine): реализован provably-fair RNG на HMAC-SHA256

Добавлен byteGenerator, floats-конвертер и verify-функция.
Покрыто тестами на детерминизм.

Agent: claude-sonnet-2026-08-17-A
Task: T-014
```

### 2.4 Конфликты
При конфликте — **не перезаписывай чужое**. Разреши вручную, сохранив обе смысловые части.
В `agents/JOURNAL.md` и `agents/STATE.md` конфликты решаются **слиянием, а не выбором**:
обе записи должны остаться.

### 2.5 Что НИКОГДА не коммитить
- Токены, ключи, пароли, `.env`, приватные seed'ы.
- `node_modules/`, `__pycache__/`, `dist/`, `build/`, `.venv/`.
- Бинарники > 10 МБ.
- Реальные персональные данные.

Если случайно закоммитил секрет — **немедленно** сообщи владельцу и отзови токен.
Ротация токена обязательна, простого удаления из истории недостаточно.

## 3. Идентификация агента

В начале смены выбери себе ID вида:

```
<модель>-<YYYY-MM-DD>-<буква>
```
Примеры: `claude-2026-08-17-A`, `gpt5-2026-08-17-B`, `gemini-2026-08-18-A`.

Буква инкрементируется, если в этот день уже работал агент той же модели.
Этот ID используется в коммитах, локах и журнале.

## 4. Блокировки — как не мешать параллельным агентам

Каталог `agents/locks/` — простая файловая система блокировок.

### 4.1 Взять лок
Создай файл `agents/locks/<область>.lock` с содержимым:

```yaml
agent: claude-2026-08-17-A
task: T-014
scope: src/engine/**
started: 2026-08-17T14:30:00Z
expires: 2026-08-17T18:30:00Z
note: реализую RNG и математику слота
```

Затем **сразу** закоммить и запушь лок:
```bash
git add agents/locks/ && git commit -m "chore(agents): лок на src/engine (T-014)" && git push
```

Если push отклонён — сделай `git pull --rebase` и проверь, не занял ли кто-то область раньше.
**Кто первым запушил лок — тот и владеет областью.**

### 4.2 Уважать чужие локи
Перед правкой файла проверь `agents/locks/`. Если область занята и лок не истёк —
**возьми другую задачу**. Не редактируй занятые файлы.

### 4.3 Истёкшие локи
Лок с `expires` в прошлом считается «мёртвым». Его можно снять, но:
1. Запиши в `agents/JOURNAL.md` факт снятия чужого мёртвого лока.
2. Не откатывай незакоммиченную чужую работу (её всё равно не видно — работай поверх).

### 4.4 Снять свой лок
Удали файл лока и запушь в том же коммите, где закрываешь смену.

### 4.5 Гранулярность
Локи ставятся на **области**, а не на весь репозиторий:
`engine`, `math`, `research`, `docs`, `frontend`, `backend`, `infra`.
Файлы `agents/STATE.md`, `agents/JOURNAL.md`, `agents/TASKS.md` **не блокируются** —
они правятся всеми, конфликты решаются слиянием.

## 5. Протокол смены

### 5.1 Начало смены — чеклист

- [ ] `git pull --rebase origin main`
- [ ] Прочитал `AGENTS.md` (этот файл)
- [ ] Прочитал `agents/STATE.md`
- [ ] Прочитал `agents/HANDOFF.md`
- [ ] Прочитал `agents/TASKS.md`
- [ ] Прочитал последние 50 строк `agents/JOURNAL.md`
- [ ] Проверил `agents/locks/`
- [ ] Выбрал agent-ID
- [ ] Выбрал задачу, поставил лок, запушил лок
- [ ] Добавил запись «SHIFT START» в `agents/JOURNAL.md`

### 5.2 Во время работы

- Коммить каждый логический шаг, пушить сразу.
- Если задача породила новые задачи — добавь их в `agents/TASKS.md` с новыми ID.
- Если принял архитектурное решение — запиши ADR в `agents/DECISIONS.md`.
- Если нашёл важный внешний источник — добавь в `research/SOURCES.md`.
- Если что-то сломал и не починил — **обязательно** зафиксируй в `HANDOFF.md` раздел «Известные проблемы».

### 5.3 Конец смены — чеклист

- [ ] Обновил `agents/STATE.md` (что сделано, что изменилось, актуальная стадия)
- [ ] Переписал `agents/HANDOFF.md` под следующего агента
- [ ] Актуализировал статусы в `agents/TASKS.md`
- [ ] Добавил запись «SHIFT END» в `agents/JOURNAL.md`
- [ ] Снял свой лок
- [ ] Прогнал проверки локально (см. §5.4) — CI не должен быть первым, кто узнает о поломке
- [ ] `git add -A && git commit && git push`
- [ ] Убедился, что push прошёл (`git status` чистый, `git log origin/main -1`)

**Смена без выполненного чеклиста 5.3 = потерянный контекст.**

### 5.4 Проверки перед пушем

```bash
npm test                            # движок: типы, RNG, математика, лимиты
npm run client:test                 # клиент: логика показа + фикстуры на барабанах
python3 tests/test_round.py         # эталонный раунд
python3 scripts/crosscheck.py       # Python <-> TypeScript
python3 scripts/check_protocol.py   # дисциплина агентов
```

То же самое запускается в CI (`.github/workflows/ci.yml`) на каждый push
и pull request, четырьмя параллельными задачами: `engine`, `client`,
`math`, `protocol`.

**`scripts/check_protocol.py` проверяет именно протокол, а не код:**

| Что проверяет | Почему это важно при параллельной работе |
|---|---|
| Файлы контекста на месте и не пусты | Без них следующий агент начинает с нуля |
| Локи разбираются и содержат все поля | Битый лок не защищает область |
| Просроченные локи | Предупреждение: агент мог упасть, область свободна |
| Счётчики «следующий свободный ID» | Два агента с одним «следующим T-024» создадут дубль |
| Ссылки в markdown ведут в существующие файлы | Агент не откроет ссылку глазами и не заметит битую |
| `JOURNAL.md` только дополняется | Переписанная запись = стёртая история решений |
| Свежесть `STATE.md` относительно кода | Ловит ровно то нарушение, о котором говорит золотое правило |

Ошибки роняют сборку. Просроченный лок и отставший `STATE.md` — только
предупреждения: это поводы разобраться, а не блокировать мерж.

## 6. Формат записи в JOURNAL.md

Append-only. Новые записи **вниз**. Прошлые не редактируются и не удаляются.

```markdown
## 2026-08-17 — claude-2026-08-17-A

**SHIFT START** 14:30 UTC
Задачи: T-014, T-015
Локи: `engine`

### Сделано
- Реализован provably-fair RNG (`src/engine/rng.js`)
- Добавлена таблица выплат в `docs/MATH.md`

### Решения
- ADR-003: используем HMAC-SHA256 вместо VRF на первом этапе (см. DECISIONS.md)

### Проблемы / не доделано
- Симулятор RTP даёт 94.2% вместо целевых 96% — нужна перебалансировка reel strips (T-016)

### Для следующего агента
- Начни с T-016. Файл `scripts/simulate.py`, крути веса в `config/reels.json`.

**SHIFT END** 18:10 UTC
```

## 7. Формат TASKS.md

```markdown
| ID | Задача | Приоритет | Статус | Агент | Обновлено |
|----|--------|-----------|--------|-------|-----------|
| T-001 | Описание | P0 | done | claude-2026-08-17-A | 2026-08-17 |
```

Статусы: `todo` → `in-progress` → `blocked` / `review` → `done` / `cancelled`.
Приоритеты: `P0` (критично), `P1` (важно), `P2` (желательно), `P3` (потом).

**ID никогда не переиспользуются.** Новая задача = следующий свободный номер.

## 8. Формат DECISIONS.md (ADR)

```markdown
## ADR-00X: Заголовок решения

- **Дата:** 2026-08-17
- **Агент:** claude-2026-08-17-A
- **Статус:** предложено / принято / заменено ADR-00Y / отменено

### Контекст
Что за проблема, какие ограничения.

### Решение
Что решили.

### Альтернативы
Что рассматривали и почему отвергли.

### Последствия
Что это даёт и чем придётся заплатить.
```

ADR **не удаляются**. Устаревшие помечаются `заменено ADR-00Y`.

## 9. Правила исследования

Когда агент проводит ресёрч:

1. Результат кладётся в `research/` отдельным `.md` файлом с датой в шапке.
2. **Каждое фактическое утверждение — со ссылкой на источник.** Без ссылки — помечай `[непроверено]`.
3. Все URL дублируй в `research/SOURCES.md` с датой доступа.
4. Указывай дату актуальности: цены, законы и правила регуляторов меняются каждый год.
5. Разделяй **факт** и **оценку/мнение**. Мнения помечай `[оценка]`.
6. Противоречивые данные из разных источников — приводи оба и отмечай расхождение.

## 10. Правила кода

- Язык комментариев и документации — **русский**. Идентификаторы в коде — английский.
- Любая RNG-логика — **только на сервере**. Клиентская случайность недопустима.
- Криптография — только CSPRNG: `crypto.randomBytes`, `crypto.getRandomValues`,
  `secrets` (Python), `java.security.SecureRandom`. Никогда `Math.random()`.
- Деньги — только целые числа (минимальные единицы/центы). Никогда `float` для баланса.
- Все денежные операции — через транзакции БД с идемпотентными ключами.
- Каждый игровой раунд логируется целиком: seeds, nonce, bet, outcome, payout, timestamp.
- Новый функционал — с тестами. Математика слота — с симуляцией ≥ 10 млн спинов.

## 11. Юридическая рамка — читать обязательно

Проект носит **исследовательский и технический** характер.

- Азартные игры на реальные деньги регулируются практически везде.
  Запуск без лицензии — уголовная/административная ответственность во многих юрисдикциях.
- **В Украине** онлайн-гемблинг регулируется отдельно; требуется лицензия
  и соблюдение национального законодательства. Проверяй актуальный статус регулятора
  перед любыми действиями с реальными деньгами.
- Работа с реальными деньгами **не начинается** до получения лицензии,
  сертификации RNG и настройки KYC/AML.
- До этого момента проект развивается как:
  - демо/симулятор на виртуальных фишках без возможности покупки и вывода,
  - или как B2B-движок/математика для лицензированных операторов.

Агент, который добавляет функционал приёма реальных платежей без явного
подтверждённого лицензионного статуса в `agents/STATE.md`, **нарушает протокол**.

## 12. Что делать при неопределённости

1. Ищи ответ в `agents/DECISIONS.md` и `research/`.
2. Если ответа нет — прими решение, **зафиксируй ADR** и пометь `Статус: предложено`.
3. Спорные вопросы, требующие владельца, складывай в `agents/QUESTIONS.md`.
4. Никогда не удаляй чужую работу «потому что мне кажется, что лучше иначе».
   Предложи альтернативу в ADR.

## 13. Анти-паттерны (не делай так)

| ❌ Плохо | ✅ Хорошо |
|---|---|
| Один гигантский коммит в конце | Атомарные коммиты + push сразу |
| Работа без `git pull` | Всегда rebase перед стартом |
| Правка занятой локом области | Взять другую задачу |
| «Я всё помню, запишу потом» | STATE/JOURNAL обновляются в ту же смену |
| Переписывание чужого JOURNAL | Append-only, только вниз |
| `Math.random()` в игровой логике | CSPRNG на сервере |
| Баланс во `float` | Целые минимальные единицы |
| Факты без источников в research | Каждое утверждение со ссылкой |
| Force-push в main | Никогда. Только merge/rebase |
