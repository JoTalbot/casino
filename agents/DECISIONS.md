## ADR-001: Модель мультиагентной работы — файловые локи + append-only журнал

- **Дата:** 2026-08-17
- **Агент:** claude-2026-08-17-A
- **Статус:** принято

### Контекст
Над проектом работают разные ИИ-агенты с разных машин, в разное время и параллельно.
У агентов нет общей памяти между сессиями. Нужен механизм, который:
(а) сохраняет контекст между сменами, (б) предотвращает конфликты при параллельной работе,
(в) работает без внешних сервисов — только через git.

### Решение
Трёхуровневая система, целиком внутри репозитория:

1. **Состояние** — `agents/STATE.md` (снимок «где мы») и `agents/HANDOFF.md`
   (адресное сообщение следующему агенту). Перезаписываются каждую смену.
2. **История** — `agents/JOURNAL.md`, append-only. Никогда не редактируется,
   при merge-конфликте сохраняются обе записи. Даёт полную археологию проекта.
3. **Координация** — `agents/locks/*.lock`, файлы-блокировки по областям
   (`engine`, `math`, `research`, `docs`, `frontend`, `backend`, `infra`) с полем `expires`.
   Разрешение гонок: кто первым **запушил** лок — тот владеет областью.

Плюс `TASKS.md` (очередь с неповторяющимися ID), `DECISIONS.md` (этот файл),
`QUESTIONS.md` (вопросы к владельцу), `GLOSSARY.md` (термины отрасли).

### Альтернативы
- **GitHub Issues/Projects как источник правды** — отвергнуто: требует API-доступа и токена
  у каждого агента, не читается одной командой `cat`, теряется при клонировании.
- **Git-ветки на агента** — отвергнуто: владелец требует пушить правки сразу в main;
  ветки создают отложенные merge-конфликты и «невидимую» работу.
- **Блокировка всего репозитория одним локом** — отвергнуто: убивает параллелизм,
  ради которого всё и затевалось.
- **Только README с заметками** — отвергнуто: не масштабируется, контекст размывается.

### Последствия
**Плюсы:** нулевые внешние зависимости; весь контекст восстанавливается за одну команду
`cat AGENTS.md agents/STATE.md agents/HANDOFF.md`; параллельная работа возможна;
полная история решений.
**Минусы:** дисциплина держится на добровольном соблюдении протокола агентами;
локи «мягкие» — технически не мешают записи; требуется ручное обновление файлов
в конце каждой смены. Частично лечится задачей T-018 (CI-проверка, что STATE.md обновлён).

## ADR-002: Provably fair RNG на HMAC-SHA256 (commit-reveal) как базовая схема

- **Дата:** 2026-08-17
- **Агент:** claude-2026-08-17-A
- **Статус:** принято (для прототипа), может быть дополнено при выходе на лицензию

### Контекст
Нужен генератор случайных исходов, который: (а) криптостойкий,
(б) проверяемый игроком постфактум, (в) не требует на старте дорогой сертификации,
(г) является отраслевым стандартом, знакомым игрокам.

### Решение
Классическая схема commit-reveal, ставшая индустриальным стандартом
после её популяризации Stake:

```
1. Сервер генерирует serverSeed (64 hex-символа, CSPRNG)
2. Сервер публикует SHA256(serverSeed) ДО ставок       ← коммитмент
3. Игрок задаёт свой clientSeed                        ← влияние игрока
4. Каждая ставка увеличивает nonce
5. Байты исхода = HMAC_SHA256(serverSeed, "clientSeed:nonce:round")
6. При ротации seed сервер раскрывает serverSeed
7. Игрок проверяет: SHA256(раскрытый) == опубликованный хэш
                    и пересчитывает исход сам
```

Байты преобразуются во float через деление на степени 256 и далее — в индексы
позиций барабанов согласно reel strips.

### Альтернативы
- **Чистый серверный CSPRNG без верификации** — отвергнуто для прототипа: игрок
  не может проверить честность, требует доверия к оператору и сертификата лаборатории
  как единственного аргумента. Останется нужен дополнительно при лицензировании.
- **Chainlink VRF / ORAO VRF (on-chain)** — отвергнуто на первом этапе: дорого по газу
  на каждый спин, высокая латентность, привязка к блокчейну. Разумно для джекпотов
  и крипто-направления — оставляем как возможное расширение.
- **Клиентская генерация** — отвергнуто категорически: тривиально ломается,
  недопустимо ни в одной регулируемой юрисдикции.

### Последствия
**Плюсы:** проверяемость без доверия к оператору; понятная игрокам схема;
дёшево в реализации; отлично ложится на детерминированные тесты.
**Минусы:** не заменяет сертификацию RNG для регулируемых рынков — при выходе
на лицензию всё равно потребуется аудит GLI-11 / iTech Labs / eCOGRA.
Требует аккуратного хранения seed'ов и полного аудит-лога раундов.
Известная тонкость: наивная конвертация байтов во float даёт неравномерность —
конвертер нужно покрыть статистическими тестами.

## ADR-003: Русский язык документации, английский — в коде

- **Дата:** 2026-08-17
- **Агент:** claude-2026-08-17-A
- **Статус:** принято

### Контекст
Владелец проекта требует общения и материалов на русском.
При этом код должен оставаться пригодным для внешнего аудита, найма
и потенциальной подачи в сертификационную лабораторию.

### Решение
- Вся документация, `research/`, `agents/`, комментарии в коде, сообщения коммитов — **русский**.
- Идентификаторы, имена файлов, API-поля, схема БД, ключи конфигов — **английский**.
- Документы, предназначенные для внешних сторон (PAR sheet для лаборатории,
  техническая спецификация для регулятора) — дублируются на английском при необходимости.

### Альтернативы
- **Всё на английском** — отвергнуто: противоречит требованию владельца.
- **Всё на русском включая код** — отвергнуто: кириллические идентификаторы ломают
  инструменты, мешают аудиту и найму.

### Последствия
**Плюсы:** владелец читает всё без перевода; код остаётся индустриально стандартным.
**Минусы:** при подаче на сертификацию часть документации придётся переводить —
это заранее заложено в план (стадия 7).

## ADR-004: Продукт стадии 1 — соц-казино на виртуальных фишках (ответ на Q-001)

- **Дата:** 2026-08-17
- **Агент:** claude-2026-08-17-B
- **Статус:** принято (предварительно, до подтверждения владельцем)

### Контекст
Q-001 блокировал T-006, T-010, T-011, T-014, T-016 — то есть выбор стека,
клиента и юрисдикции. Владелец дал команду «делай всё» и работать автономно,
явного ответа на Q-001 не поступало. Дальнейший простой обходится дороже,
чем принятое и явно помеченное решение, которое легко откатить.

Ключевое наблюдение из `research/`: варианты A, B и C отличаются **обвязкой**
(платежи, KYC, лицензия, договоры), но разделяют **одно и то же ядро** —
математику слота, RNG, игровой сервер, аудит-лог и клиент. Ядро строится
одинаково в любом сценарии, поэтому его разработка не должна ждать
юридического решения.

### Решение
Стадия 1 проекта — **вариант A: соц-казино / демо на виртуальных фишках**.

- Валюта — виртуальные фишки без покупки за реальные деньги и без вывода.
- Никаких платёжных провайдеров, KYC и лицензии на этой стадии.
- Ядро (математика, RNG, сервер, БД, клиент) проектируется так, чтобы
  переход к B или C не требовал переписывания: денежные величины хранятся
  целыми числами в минимальных единицах, кошелёк изолирован за интерфейсом,
  аудит-лог раундов ведётся с первого дня, PAR sheet генерируется автоматически.
- Юридический трек (Q-002, Q-003, Q-004, T-016, T-017) идёт **параллельно**
  и не блокирует разработку.

Граница отката: если владелец выберет B или C, выброшенной оказывается только
обвязка соц-казино (магазин фишек, отсутствие KYC) — ядро сохраняется целиком.

### Альтернативы
- **Ждать ответа владельца** — отвергнуто: прямая команда работать автономно,
  а простой блокирует пять задач.
- **Сразу вариант C (лицензированный оператор)** — отвергнуто: $75–250k,
  9–12 месяцев, требует решений по юрисдикции и бюджету, которых нет.
- **Вариант B (B2B-движок)** — отвергнуто как стартовая точка: продажа
  операторам требует сертификации GLI/iTech, то есть готового и проверенного
  ядра. B достижим ИЗ A, но не наоборот.

### Последствия
**Плюсы:** разработка стартует немедленно; юридический риск на стадии 1
близок к нулю; ядро полностью переиспользуется в B и C; можно показывать
рабочий продукт до любых вложений в лицензию.
**Минусы:** нулевая выручка на стадии 1; часть требований реальных денег
(лимиты ответственной игры, KYC, сверка кошелька) придётся проектировать
«на вырост», без возможности проверить их в бою.
**Риск:** решение принято без явного подтверждения владельца — помечено как
предварительное. При возражении откатывается сменой статуса ADR и
разблокировкой Q-001; выполненная работа по ядру не теряется.

## ADR-005: Стек бэкенда — TypeScript на Node.js, Fastify, PostgreSQL (ответ на T-010)

- **Дата:** 2026-08-17
- **Агент:** claude-2026-08-17-B
- **Статус:** принято

### Контекст
Нужен игровой сервер (RGS), реализующий `api/openapi.yaml`: спин, верификация,
история, кошелёк. Нагрузка стадии 1 — десятки одновременных игроков, то есть
производительность фреймворка заведомо не является узким местом. Узкое место —
корректность денежных операций и скорость разработки одним-двумя агентами.

Уже существует и протестировано: `src/engine/rng.ts` — provably fair RNG на
TypeScript, 40 проходящих тестов. Математика и калибровка лент написаны на
Python (`slotmath/`) и остаются офлайн-инструментом.

Обзор рынка 2026 (см. `research/SOURCES.md`): Fastify даёт ~65k req/s против
~15k у Express и ~18k у NestJS на Express-адаптере; NestJS на Fastify-адаптере
выходит на ~55k. Разница в реальной нагрузке с обращениями к БД смазывается —
решающим фактором становится не бенчмарк, а объём церемоний.

### Решение
- **Язык:** TypeScript, `strict`, ES2022, NodeNext — как уже настроено
  в `tsconfig.json`.
- **Рантайм:** Node.js 20 LTS. Не Bun и не Deno.
- **HTTP-фреймворк:** **Fastify 5**.
- **Валидация:** **Zod**, схемы выводятся из тех же типов, что использует код.
  Единый источник правды по форме запроса — TypeScript, а не отдельный
  JSON Schema.
- **БД:** **PostgreSQL 16**, доступ через `pg` + слой запросов с явным SQL.
  ORM не берём.
- **Миграции:** нумерованные SQL-файлы, применяются простым раннером.
- **Кэш и rate limiting:** Redis, подключается когда появится нагрузка,
  не раньше. На стадии 1 — in-memory.
- **Математика на сервере:** порт `slotmath` на TypeScript. Python остаётся
  офлайн-инструментом калибровки и симуляции; сервер не вызывает Python
  в рантайме.

### Альтернативы
- **NestJS** — самая частая «дефолтная» рекомендация 2026 для команд от трёх
  человек. Отвергнут: декораторы, модули и DI-контейнер дают заметный
  boilerplate на API из тринадцати путей, а главную нашу проблему —
  корректность транзакций — не решают вовсе. Для агента, который читает
  проект с нуля каждую смену, явный код важнее развесистой структуры.
- **Go** — привлекателен: `slotopol/server` написан на Go и доказывает, что
  язык подходит для слотов идеально (быстрый перебор комбинаций в сканере).
  Отвергнут по одной причине: RNG уже написан и оттестирован на TypeScript,
  и переписывание криптографического кода — самый дорогой способ внести
  уязвимость. К Go можно вернуться, если упрёмся в производительность
  сканера, — но сканер это офлайн-инструмент, а не сервер.
- **Python (FastAPI)** — соблазнительно, потому что вся математика уже на
  Python. Отвергнут: RNG на TypeScript пришлось бы дублировать, а два
  независимых генератора в одном продукте — гарантированное расхождение.
- **Bun / Deno** — быстрее и приятнее, но для денежного сервиса важнее
  предсказуемость и зрелость экосистемы драйверов PostgreSQL.
- **Prisma / TypeORM** — отвергнуты сознательно. Наш кошелёк построен на
  двойной записи с триггером, `SELECT ... FOR UPDATE` на паре сидов,
  частичных уникальных индексах и правилах `DO INSTEAD NOTHING`. Всё это
  ORM либо не выражает, либо выражает через escape hatch к сырому SQL.
  Когда критичный путь всё равно пишется руками, ORM остаётся лишним слоем,
  скрывающим план запроса.
- **Encore.ts** — интересные цифры (~121k req/s), но это фреймворк с
  автоматическим провижинингом инфраструктуры в AWS/GCP и соответствующей
  привязкой. Для проекта, который может оказаться где угодно, включая
  собственный VPS, привязка неприемлема.

### Последствия
**Плюсы:** один язык от RNG до API; Fastify не мешает и не диктует структуру;
явный SQL означает, что каждый денежный запрос видно целиком; Zod даёт
валидацию и типы из одного объявления; порог входа для следующего агента
минимален.
**Минусы:** придётся написать руками то, что NestJS даёт из коробки — DI,
структуру модулей, обработку ошибок; отсутствие ORM означает больше кода для
рутинных выборок; порт математики на TypeScript — отдельная задача с риском
расхождения с Python-версией.
**Митигация расхождения:** порт `slotmath` на TypeScript обязан проходить
проверку соответствия — те же ленты и тот же конфиг должны давать тот же
аналитический RTP до шестого знака и тот же результат на фиксированных сидах.
Это условие приёмки соответствующей задачи.

## ADR-006: Стек клиента — TypeScript + PixiJS v8, за основу берётся pixi-reels (ответ на T-011)

- **Дата:** 2026-08-17
- **Агент:** claude-2026-08-17-B
- **Статус:** принято

### Контекст
Нужен клиент слота 5×3 на 20 линий (T-014). Ключевое ограничение из
`docs/API.md`: **клиент ничего не решает**, он получает от сервера готовый
результат — позиции остановки барабанов, сетку символов и разбор выигрыша —
и обязан его показать. То есть от клиента требуется рендер, анимация и
состояние интерфейса, но не игровая логика.

Общая рекомендация индустрии на 2026 год звучит «для игр берите Phaser 4,
PixiJS — это рендерер, а не фреймворк». Для типичной игры это верно: Phaser
даёт физику, сцены, ввод, звук, тайлмапы, камеры. Слот не использует почти
ничего из этого списка.

Разбор OSS (`research/06-OSS-REVIEW.md` §2) показал сложившуюся экосистему
именно вокруг Pixi: `pixi-reels` (MIT, PixiJS v8 + GSAP), `asiryk/slot-game`,
`weyoss/pixi-slot-machine`, `xhulianomalaj/Slot-Game` — последний использует
`pixi-reels` и добавляет Playwright + Vitest.

### Решение
- **Рендер:** **PixiJS v8** (WebGPU с откатом на WebGL 2).
- **Основа барабанов:** **`schmooky/pixi-reels`** (MIT) — fluent-builder,
  типизированные события, настраиваемые фазы спина, win-presenters,
  headless-тестирование в Node без PixiJS.
  В npm пакет называется просто **`pixi-reels`** (проверено на v2.2.0),
  без scope. Вариантов `@schmooky/pixi-reels` и `@schmooky/reels`
  в реестре нет — оба дают 404, не тратьте на них время.
- **Анимации:** GSAP (уже зависимость `pixi-reels`).
- **Состояние интерфейса:** конечный автомат на чистом TypeScript
  (`idle → betting → spinning → revealing → freespins → settled`).
  Без MobX и без React в игровом слое.
- **Сборка:** Vite.
- **Тесты:** Vitest на логику и headless-барабаны, Playwright на сценарий
  «спин → анимация → баланс обновился».
- **Обёртка интерфейса** (лобби, история, настройки сидов, лимиты) — обычный
  DOM/HTML поверх канваса, не игровой движок.

### Альтернативы
- **Phaser 4** — отвергнут. Его сильные стороны (физика Arcade/Matter,
  тайлмапы, камеры, менеджер сцен, гейпад) в слоте не нужны ни одна.
  Взамен платим тремя вещами: бандл ~1.2 МБ против ~450 КБ у Pixi (для
  веб-игры время загрузки прямо влияет на удержание), собственный рендерер
  без WebGPU в Phaser 4, и отсутствие готовых слот-компонентов — барабаны
  всё равно пришлось бы писать с нуля. Аргумент «Phaser даёт больше из
  коробки» разворачивается против себя: в нашем случае из коробки даёт
  больше как раз Pixi, потому что для Pixi есть `pixi-reels`.
- **Three.js / Babylon.js (3D-слот)** — отвергнуты: 3D повышает стоимость
  арта в разы и ничего не добавляет к продукту стадии 1.
- **Написать барабаны с нуля на голом Pixi** — отвергнуто. `pixi-reels`
  под MIT уже решает ровно нашу задачу, включая рецепты для линий,
  скаттеров, фриспинов, каскадов, hold&win, sticky wilds и anticipation.
  Форк всегда возможен, лицензия позволяет.
- **React + PixiJS в игровом слое** (как `ktsalik/sloticon`) — отвергнуто:
  реконсиляция React в цикле рендера 60 fps даёт только накладные расходы.
  React допустим для обёртки интерфейса, если понадобится.

### Риск и его проверка
В примерах `pixi-reels` символы выбираются **на клиенте по весам**
(`.weights()`). Нам это категорически не подходит: результат приходит с
сервера. Первое, что делается в T-014, — проверка, что библиотека принимает
явно заданные позиции остановки и сетку в обход собственного выбора.

Если такого API нет — форкаем (MIT позволяет) и вырезаем клиентский выбор
символов совсем, чтобы его нельзя было включить случайно. Это не «может быть
придётся», а желаемое состояние: в коде клиента не должно быть ни одной
строки, способной сгенерировать результат.

**Риск снят в T-014 (2026-08-17).** Такое API есть:
`reelSet.setResult(ColumnTarget[])` задаёт итоговую сетку явно, а
`ColumnTarget.visible[row]` индексируется так же, как `grid[reel][row]`
нашего движка. `.weights()` и `.rng()` влияют **только** на символы,
мелькающие во время вращения, и на исход не действуют. Форк не нужен.
Проверено не рассуждением, а тестом: `client/src/reels.test.ts` прогоняет
все 136 спинов из `tests/fixtures/rounds.json` через настоящий `ReelSet`
в headless-режиме и сверяет каждую ячейку с серверной сеткой.

### Последствия
**Плюсы:** бандл втрое меньше Phaser; WebGPU из коробки; готовая библиотека
барабанов под MIT; headless-тесты барабанов без браузера; есть публичный
пример интеграции с тестовым контуром.
**Минусы:** Pixi не даёт звук, ввод и менеджер сцен — берём отдельные
библиотеки или пишем сами (для слота это десятки строк, не сотни);
зависимость от небольшого проекта `pixi-reels` — митигируется тем, что
лицензия MIT и форк не потребует разрешения.

## ADR-007: Коридор приёмки RTP привязывается к объёму выборки (ответ на T-019)

- **Дата:** 2026-08-17
- **Агент:** claude-2026-08-17-B
- **Статус:** принято

### Контекст

В критериях приёмки (T-007) зафиксирован коридор RTP **95.5–96.5%** —
плоский, без привязки к числу сыгранных раундов. Пока речь шла о
симуляции на 10 млн спинов, это работало. Но тот же коридор напрашивается
использовать и для мониторинга живой игры, и вот там он становится
вредным.

Расчёт T-019 (`scripts/confidence.py`, `simulations/confidence.json`)
показывает масштаб проблемы. При sigma = 4.126 ставки за раунд доля
**честных** прогонов, выходящих за коридор 95.5–96.5%:

| Раундов | Вне коридора |
| ---: | ---: |
| 1 000 | 96.7% |
| 10 000 | 90.3% |
| 100 000 | 70.6% |
| 1 000 000 | 22.4% |
| 5 000 000 | 0.7% |

То есть на дневном объёме небольшого проекта плоский коридор срабатывает
почти всегда, и срабатывает ложно. Алерт, который загорается в 90%
случаев при полностью исправной математике, — это не алерт.

### Решение

1. **Коридор 95.5–96.5% остаётся, но только для приёмки математики**
   на выборке ≥ 5 млн раундов (симуляция, релиз новой версии `game.json`).
   Там он осмыслен: ложное срабатывание 0.7%.

2. **Мониторинг живой игры сравнивает наблюдаемый RTP с доверительным
   интервалом, посчитанным на фактическом числе раундов**, а не с плоским
   коридором. Граница берётся из `half_width_pp(sigma, n, 0.999)`:
   три с половиной сигмы, чтобы алерт означал проблему, а не шум.

3. **Ниже 100 000 раундов алерт по RTP не выставляется вообще.**
   Интервал там шире самого коридора, и любое значение внутри него
   не несёт информации. На малых объёмах контролируются другие вещи:
   совпадение `configHash`, воспроизводимость раундов по сидам,
   отсутствие расхождений между движком и верификатором. Эти проверки
   детерминированы и ловят подмену математики мгновенно, не дожидаясь
   статистики.

4. **Асимметрия учитывается явно.** На горизонтах до ~50 тыс. раундов
   верхний хвост распределения наблюдаемого RTP в 1.1–1.5 раза длиннее
   нижнего (редкие крупные выплаты тянут вверх, вниз ограничивает ноль).
   Поэтому границы алерта берутся из **эмпирических перцентилей
   бутстрапа**, а не из симметричной формулы `±z*sigma/sqrt(n)`.

### Последствия

**Плюсы:** мониторинг перестаёт быть генератором ложных тревог; появляется
честный ответ игроку на жалобу «RTP занижен» — сессия в 1 000 спинов с
возвратом 75% лежит внутри нормального разброса; требования к банкроллу
(987 ставок под риск 1%) посчитаны и проверены Monte Carlo.

**Минусы:** мониторинг усложняется — нужно хранить счётчик раундов и
пересчитывать границу, а не сравнивать с константой. Границы зависят от
sigma, то есть **при любой смене математики их надо пересчитывать**:
`python3 scripts/confidence.py` добавлен в чек-лист релиза `game.json`.

**Что это не отменяет:** сам целевой RTP 95.9778% и потолок 5 000x
остаются как были. Решение касается только того, как мы проверяем
соответствие факта теории.

## ADR-008: Вторая игра на том же движке — проверка переиспользуемости (ответ на T-029)

- **Дата:** 2026-08-19
- **Агент:** arena-2026-08-19-H / arena-2026-08-19-I
- **Статус:** принято

### Контекст
T-029 требует доказать, что игровой движок не заточен под одну игру Crown of Fortune. Если математика второй игры требует переписывания движка, архитектура ошибочна: каждая новая игра должна быть новым JSON, а не новым кодом.

### Решение
- Добавлен `config/second-game.json` — Crown of Fortune II v1.1.0, те же ленты и символы, другое имя/версия (RTP тот же для простоты). Файл собирается тем же `build_game.py`, хэш считается той же функцией `configHash`.
- Создан `src/server/gameRegistry.ts`: `loadGames()` сканирует известные пути (game.json + second-game.json), возвращает Map<code, LoadedConfig>. `ensureAllGames()` гарантирует наличие строк в `games` и `game_configs` в БД.
- `src/server/app.ts`: `/api/v1/games` возвращает обе игры, `/games/:code` поддерживает оба кода, `POST /rounds` принимает `gameCode` из enum `["crown-of-fortune","crown-of-fortune-ii"]` и выбирает соответствующую LoadedConfig для `settleRound`.
- `roundService.ts` принимает `gameCode` параметром и ищет игру по коду, а не хардкодом.
- Добавлен тест `src/engine/multiGame.test.ts`: один и тот же `playRound` играет раунд на обеих конфигурациях детерминированно.

### Альтернативы
- **Хранить конфиги только в БД** — отвергнуто: БД — кэш, источник правды — JSON в репозитории, который версионируется и хэшируется. БД синхронизируется из JSON.
- **Отдельный движок на игру** — отвергнуто: дублирование кода, расхождение RTP.
- **Динамический скан `config/*.json` без белого списка** — отложено: пока 2 игры, хардкод проще и безопаснее (не подхватит временные файлы). При 5+ играх перейти на скан с фильтром.

### Последствия
**Плюсы:** доказана переиспользуемость: новая игра = новый JSON + строка в реестре игр. Нет новой логики раунда.
**Минусы:** пока нет автоматического открытия игр из папки, добавление третьей игры требует правки `gameRegistry.ts` и `app.ts`. Это намеренный компромисс стадии.

## ADR-009: Возрастной гейт 18+ и ToS/Privacy для соц-казино (ответ на T-025, часть T-024)

### Последствия
**Плюсы:** закрыты требования Google Play по RG и Apple по 18+; пользователь видит правила и понимает что фишки без ценности; гейт реализован без бэкенда.
**Минусы:** гейт обходится очисткой кэша — для регулируемого рынка нужен нативный рейтинг и серверная проверка даты рождения (стадия 6+).

## ADR-010: Деплой, админка, графики, история, верификатор, rate limiting и reality check (ответ на T-030-T-041)

- **Reality check только в логе** — отвергнуто: модалка заметнее и соответствует требованию регуляторов «напоминание должно прерывать игру».

### Последствия
**Плюсы:** деплой одной командой `docker compose up`, админка с грантами и блоком, история и верификатор в клиенте, защита от спама спинов, напоминание о времени.

## ADR-012: Рефералка, ачивки, чат, бэкап, мобильная адаптация (ответ на T-059…T-063 и T-054…T-058 продолжение)

- **Дата:** 2026-08-19
- **Агент:** arena-2026-08-19-N / arena-2026-08-19-M
- **Статус:** принято

### Контекст
После закрытия деплоя, админки, истории и т.д. соц-казино требует социальных механик для удержания: рефералка (пригласи друга — получи CHIP), ачивки (first win, big win, 100 спинов, referral master), чат для лобби, бэкап скрипт для PG, мобильная адаптация.

### Решение

**Рефералка (T-059):**
- Таблица `referrals` (referrer_id, referee_id, bonus_amount, UNIQUE referee_id), индекс по referrer.
- `POST /referrals` — принимает либо `refereeId` (текущий игрок — реферер) либо `referralCode` (текущий игрок вводит код реферера, становится рефералом). Проверка referrer != referee, ON CONFLICT DO NOTHING, начисление бонусов обоим через ledger grant с idempotency `referral:...`, audit_log.
- `GET /referrals` — список приглашённых, inviteCode = playerId, inviteLink.

**Ачивки (T-060):**
- Тип `achievement_type` ENUM, таблицы `achievements` (code, title, description, reward) и `player_achievements` (player_id, achievement_id).
- Сиды 5 ачивок: first_win 100, big_win 500, hundred_spins 1000, referral_master 2500, tournament_winner 5000.
- `checkAndUnlockAchievements()` — проверяет уже открытые, условие: first_win при любом win>0, big_win при multiple>=100, hundred_spins при COUNT rounds >=100, referral_master при COUNT referrals >=5. При разблокировке INSERT в player_achievements и grant награды через ledger.

**Чат (T-061):**
- `chat_messages` (id bigserial, player_id, username, message 1…500, created_at), индекс по created_at DESC.
- In-memory rate limiter 5 сообщений в минуту per player (Map).
- `POST /chat` — JWT, проверка длины, rate limit 429, INSERT RETURNING.
- `GET /chat?limit=` — последние N сообщений в порядке от старых к новым для UI.

**Бэкап (T-062):**
- `scripts/backup.sh` — `pg_dump $DATABASE_URL | gzip > backups/casino_YYYYMMDD_HHMMSS.sql.gz`, оставляет 7 дней, логи.

**Мобильная адаптация (T-054):**
- `@media max-width 600px` — header padding, main колонка, controls колонкой, stage canvas 100%, kv и rg-grid в 1 колонку, seed-row в колонку, footer 10px.

**Дополнительно (уже в M):**
- Daily bonus, leaderboard, master RTP, GDPR export, Playwright UI, sound, tournaments, email mock, CI e2e docker.

### Альтернативы
- **Рефералка через внешний сервис** — отвергнуто: своя таблица проще и контролируемая.
- **Ачивки через отдельный микросервис** — отвергнуто для демо.
- **Чат через WebSocket** — отложено: REST polling достаточно для 50 сообщений, WebSocket — для стадии с live-играми.

### Последствия
**Плюсы:** социальные механики удержания, бэкап, мобильный UX.
**Минусы:** чат без модерации, ачивки без прогресс-бара в UI, бэкап требует pg_dump на хосте.

## ADR-014: Tournament auto prize cron, referral progress, chat moderation, PWA offline cache, backup restore (ответ на T-069…T-073)

- **Дата:** 2026-08-19
- **Агент:** arena-2026-08-19-O / arena-2026-08-19-P
- **Статус:** принято

### Контекст
После T-063 остались: автопризы турниров, прогресс рефералки, модерация чата, офлайн кэш API, восстановление из бэкапа.

### Решение

**Tournament auto prize (T-069):**
- Добавлен сервис `prize-cron` в `docker-compose.yml` profile `cron`, который раз в сутки (sleep 86400) запускает `node /scripts/distribute_prizes.js weekly-champions`
- distribute_prizes.js уже имел логику топ-3 и grant

**Referral progress (T-070):**
- `getReferralProgress()` — COUNT referrals, target 5, progress, remaining, hasMaster
- `GET /referrals/progress` — JWT, возвращает count/target/progress

**Chat moderation (T-071):**
- BAD_WORDS фильтр в `chat.ts` containsBadWord, выбрасывает 400 если содержит запрещённые слова
- `DELETE /admin/chat/:id` в admin.ts — удаление сообщения, audit_log

**PWA offline (T-072):**
- sw.js теперь кэширует `/api/v1/games` и `/health` через fetch-then-cache-put, fallback to cache on failure

**Backup restore (T-073):**
- `scripts/restore.sh` — `gunzip -c $FILE | psql $DATABASE_URL` или `psql < $FILE`, executable

### Альтернативы
- **Cron через BullMQ** — отложено, простой shell loop достаточно
- **Chat moderation через внешний AI** — отложено для демо

### Последствия
**Плюсы:** автопризы работают в compose profile cron, реферальный прогресс виден, чат с фильтром, offline кэш API, восстановление из бэкапа одной командой.
